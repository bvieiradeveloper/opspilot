# Research: Safe Learning Reflector

## Structured assessment of the latest message

- **Decision**: Assess only the latest user message after a successful answer. Require structured output with `hasLearning` and `fact`; represent no eligible fact explicitly and validate the output before any memory operation. Permit at most one concise fact per assessment.
- **Rationale**: This directly matches the feature request, bounds stored content, and prevents the assistant's answer or earlier conversation history from becoming an accidental source of new memories.
- **Alternatives considered**: Extracting from the full transcript (could retain assistant-generated or unrelated content); unstructured free-form reflection (harder to validate); multiple facts per turn (outside the requested bounded behavior).

## Durable facts and sensitive content

- **Decision**: Retain only explicit, durable user facts or preferences. Reject one-time requests and temporary instructions. Apply a conservative sensitivity check before saving; if the candidate or source appears to contain credentials, tokens, authentication codes, or similarly sensitive access data, do not persist it. Do not include raw messages or candidate values in operational error reports.
- **Rationale**: The specification excludes secrets and ephemeral requests. A conservative no-save outcome is safer when durability or sensitivity is uncertain.
- **Alternatives considered**: Persisting every structured model result (does not enforce the feature's safety boundary); relying on a model label alone (a model can misclassify sensitive strings); logging rejected content for diagnostics (unnecessarily exposes personal or secret data).

## Response timing and failures

- **Decision**: Send the successful chat response first, then start the learning assessment and save without awaiting either operation. Attach explicit failure reporting to the background operation. A failure must not change the response already sent.
- **Rationale**: Matches the asynchronous response requirement and keeps the request path independent of learning latency.
- **Alternatives considered**: Awaiting learning before responding (adds latency and violates the requirement); silently swallowing rejected promises (hides failures); mutating the response after learning (not possible or reliable once sent).

## Memory persistence and deduplication

- **Decision**: Reuse the existing user-scoped `MemoryStore.remember` operation for learned facts, including its duplicate handling, and reuse its existing memory listing and deletion operations for forgetting. Do not introduce new tables or memory lifecycle rules.
- **Rationale**: The repository already has semantic memory persistence and user-scoped mutation; one path for explicit and learned facts preserves consistent behavior.
- **Alternatives considered**: A second learning-specific store or direct database access from the service (duplicates persistence rules and weakens MVC separation).

## Preference forgetting and ownership

- **Decision**: Expose a `forget_preference` tool to the agent with a validated preference description as its only model-controlled input. Bind the owning user ID from the validated chat request in application code. Resolve against only that user's saved memories; delete only a single unambiguous match, and otherwise leave memories unchanged and return a clarification outcome.
- **Rationale**: Tool arguments generated by a model must not choose the owner or directly identify another user's records. A no-delete-on-ambiguity rule prevents accidental removal.
- **Alternatives considered**: Accepting `userId` from tool arguments (breaks isolation); deleting the highest-ranked match regardless of ambiguity (can delete the wrong preference); deleting all matching preferences (exceeds the user's singular intent).

## Test strategy

- **Decision**: Inject assessment/model, memory store, and error reporter dependencies for deterministic unit and HTTP tests. Assert not only expected writes but also absence of writes for transient and secret-like cases, response completion before assessment completion, and strict user scoping for forgetting.
- **Rationale**: These tests prove the measurable requirements without remote model calls or nondeterministic inference.
- **Alternatives considered**: Depend on a live provider for ordinary tests (network and response variance); test only service output (misses post-response timing and request-scope wiring).
