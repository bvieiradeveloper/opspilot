# Implementation Plan: SQLite Operations Persistence

**Branch**: `003-sqlite-operations-persistence` | **Date**: 2026-10-13 | **Spec**:
[`spec.md`](./spec.md)

**Input**: Feature specification from
[`specs/003-sqlite-operations-persistence/spec.md`](./spec.md)

## Summary

Replace the process-local store used by the production composition with a SQLite-backed
`OpsStore` implemented using Node's built-in `node:sqlite` `DatabaseSync`. Keep the deterministic
mock for benchmarks, inject the production store into agent tools, seed the five canonical
services, six alerts, and three runbooks idempotently, and add filtered incident and runbook
tools. Define a shared explicit store contract because the current repository has a structural
store object but no exported `OpsStore` interface.

## Technical Context

**Language/Version**: TypeScript ESM, strict mode; Node.js 22 LTS is the project runtime baseline.
`node:sqlite` is available from Node 22.5; use the requested `DatabaseSync` API. The local
validation environment reports Node.js 24.12.0.

**Primary Dependencies**: Node built-ins (`node:sqlite`, `node:fs`, `node:path`, and
`node:crypto`); existing Zod and LangChain tool packages. No SQLite package is required.

**Storage**: SQLite file selected by `OPSPILOT_DB`, defaulting to `./data/opspilot.db`;
`:memory:` is used by isolated persistence and tool tests.

**Testing**: `node:test` through `tsx`, via `npm run test`; TypeScript validation via
`npm run typecheck`. Existing benchmark tests use the deterministic process-local mock and fake
strategies.

**Target Platform**: Node.js server process on supported Node 22 LTS and newer runtimes with
`node:sqlite`.

**Project Type**: Single TypeScript/Express web service with agent tools.

**Performance Goals**: No throughput or latency target is specified. The store serves small,
local operational datasets with synchronous, bounded SQLite operations.

**Constraints**: Use `DatabaseSync`; execute all data reads and writes using prepared statements
with bound parameters; use static DDL only for schema creation; no SQL value interpolation.
Enforce `sev1 | sev2 | sev3` for tier and severity; alert statuses `firing | resolved`;
incident statuses `open | mitigated | resolved`.
Create the parent directory for file-backed stores but not for `:memory:`. Seed with targeted
conflict handling so reruns do not overwrite operator data. Do not add or read `.env` in
application code.

**Scale/Scope**: Four tables (`services`, `alerts`, `incidents`, `runbooks`); five persistent
seed services, six alerts (three firing and three resolved), three service runbooks, and
unbounded operational incidents within SQLite capacity. The benchmark-only mock retains its
existing `catalog-api` fixture so its catalog scenario remains reproducible.

**Structure Decision**: Keep the existing single-project layout. Create `src/store/` for the
shared persistence contract, canonical seed data, and SQLite implementation; keep agent tool
schemas in `src/agents/tools.ts` and inject the SQLite store from the production composition.
Retain the in-memory benchmark mock in `src/agents/store.ts`; it may add the benchmark-only
`catalog-api` fixture beyond the five services in the persistent seed.
