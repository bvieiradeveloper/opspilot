# Data Model: War Room Web Console

## Installation Operator

The single-operator deployment has one stable `userId`, configured by the server at startup and used for chat memory and approval ownership.

| Field | Type | Rules |
|---|---|---|
| `userId` | string | Required, non-empty after trimming; supplied by server configuration, never requested from the chat user. |

This value identifies an installation's memory scope; it is not proof of authentication. Access to the API must be restricted by the deployment network perimeter.

## Conversation and Message

The backend owns conversation persistence. The browser keeps only its active conversation and rendered message list in memory for the current page session.

| Field | Type | Rules |
|---|---|---|
| `conversationId` | string | Omitted for the first message; created by the service and required for follow-up messages. |
| `message.id` | string | Client-generated stable key for rendering and retry reconciliation. |
| `message.role` | `user \| assistant` | Discriminates operator input from agent output. |
| `message.content` | string | User text or assistant Markdown; assistant content is rendered as untrusted Markdown. |
| `message.status` | `sending \| complete \| failed \| awaiting_approval` | Controls loading, retry, and pending-authorization presentation. |
| `message.trace` | typed trace event array | Present for assistant results; source order is preserved and values are rendered as text. |
| `message.approvalIds` | string array | Links each pending or decided action card to its durable approval record. |

Conversation messages are not persisted by the browser. Refreshing the page starts a new visible conversation; the backend's existing conversation and semantic-memory stores remain unchanged.

## Chat Idempotency Record

The client creates one opaque idempotency key for each new message and reuses it for retries. The API stores the key with a fingerprint of the validated request and the original response/status.

| Field | Type | Rules |
|---|---|---|
| `key` | string | Required, bounded opaque value; unique within the installation. |
| `requestFingerprint` | string | Stable digest of the normalized message and request options; a key cannot be reused with a different fingerprint. |
| `status` | `processing \| completed` | Prevents another strategy invocation while the original request is active. |
| `responseStatus` | integer or null | Original terminal chat HTTP status, including 200, 202, or a safe error response. |
| `responseBody` | JSON object or null | Original validated terminal response, replayed for an identical retry. |
| `createdAt` | ISO timestamp | Time the request was first claimed. |
| `completedAt` | ISO timestamp or null | Time the terminal response was saved. |
| `expiresAt` | ISO timestamp | Idempotency record retention deadline; retain completed records for 24 hours. |

The first request is claimed before conversation or action side effects. A duplicate with the same key and payload replays the saved terminal response; if the request is still processing, return a retryable in-progress response without invoking another strategy. Mismatched payloads receive a conflict and do not run the strategy. A record left processing by a server crash is not automatically replayed because its prior side effects may be uncertain; it remains unavailable until its 24-hour expiry is cleaned up.

## Trace Event

Trace events retain the API's discriminated event types, including `thought`, `action`, `observation`, `answer`, `plan`, `route`, `fallback`, `critique`, and `summarize`.

| Field | Type | Rules |
|---|---|---|
| `type` | known string discriminator | Determines category and event fields. Unknown future values are displayed as an unrecognized event without executing or rendering them as markup. |
| `node` | string | Identifies the execution node. |
| `tool` | supported tool name | Required for `action`; only `open_incident` and `resolve_incident` may create approval records in this release. |
| `args` | JSON object | Required for `action`; validated against that tool's Zod schema before an approval is persisted. |
| `result` | JSON-compatible value | Required for `observation`; displayed as escaped text or formatted JSON. |
| `text` / `summary` / `steps` | event-specific data | Rendered with safe text semantics. `answer.text` is represented as the response category. |

## Pending Approval

The approval store persists each proposed operational mutation in the existing SQLite database. Only a validated proposal can be approved or rejected.

| Field | Type | Rules |
|---|---|---|
| `id` | string | Unique opaque identifier, generated by the service. |
| `requestId` | string | Existing chat request associated with the proposal. |
| `conversationId` | string | Conversation that produced the proposal. |
| `userId` | string | Server-configured installation identity. |
| `tool` | `open_incident \| resolve_incident` | Allowlisted mutating tool; arbitrary tool names are rejected. |
| `arguments` | discriminated JSON object | Validated with the corresponding tool's Zod input schema. |
| `description` | string | Safe operator-facing description derived from the validated tool and arguments. |
| `status` | `pending \| executing \| executed \| rejected \| failed` | State machine described below. |
| `createdAt` | ISO timestamp | Time the pending action was stored. |
| `decidedAt` | ISO timestamp or null | Set once an approval or rejection is accepted. |
| `completedAt` | ISO timestamp or null | Set after successful or failed tool execution. |
| `result` | JSON-compatible value or null | Recorded tool result; never populated as successful before execution completes. |
| `errorCode` | string or null | Safe stable code for execution failure; internal exception details are not returned. |

### Approval state transitions

```text
pending -> rejected
pending -> executing -> executed
pending -> executing -> failed
```

- The decision endpoint atomically claims only a `pending` record.
- A `rejected` action is never invoked.
- An `executing`, terminal, unknown, or malformed record cannot be executed again.
- Repeating the same decision returns the existing state/result, so a lost HTTP response can be reconciled without repeating a mutation. A conflicting decision is rejected.
- A failed action remains failed; an operator must start a new chat/action rather than blindly replaying a possibly partial mutation.

## API Connection and Theme Settings

| Setting | Type | Rules |
|---|---|---|
| `apiBaseUrl` | absolute URL string | HTTP or HTTPS only; no embedded credentials, query, or fragment; validated before saving and normalized for endpoint joining. |
| `theme` | `system \| light \| dark` | Defaults to `system`; explicit operator choice overrides system preference. |

Only these non-secret preferences are persisted in browser storage. Do not persist chat transcripts, approval decisions, authorization tokens, or tool arguments in browser storage.
