# Data Model: Persisted Request Tracing

## Request Record

Represents one accepted chat request throughout processing.

| Field | Type | Constraints / meaning |
|---|---|---|
| `requestId` | string | Unique, non-empty identifier generated by the service; primary key and correlation key |
| `userId` | string | Non-empty identifier supplied by the accepted chat request |
| `route` | supported route or null | Selected execution route when known; null while routing is pending or unavailable |
| `status` | enum | `in_progress`, `succeeded`, `failed`, or `timed_out` |
| `startedAt` | ISO 8601 timestamp | Required; set when the accepted request is recorded |
| `completedAt` | ISO 8601 timestamp or null | Null while in progress; populated when processing ends |
| `statusCode` | integer or null | HTTP outcome for completed requests |
| `metrics` | object or null | Validated metrics available for a completed request; null if unavailable |
| `modelUsed` | string or null | Model identifier from available request metrics |
| `promptTokens` | non-negative integer or null | Actual input-token count from available request metrics; null when unavailable |
| `latencyMs` | non-negative number or null | Request/model latency from available request metrics |
| `errorCode` | string or null | Safe, stable uppercase code matching `^[A-Z][A-Z0-9_]{0,63}$`; never exception details or request content |

Lifecycle:

```text
in_progress -> succeeded
in_progress -> failed
in_progress -> timed_out
```

The store must not replace a terminal status with another terminal status. Persisting `in_progress` before running the agent allows an accepted request to remain discoverable if the service exits before finalization.

## Trace Event

An ordered event emitted during a request's execution.

| Field | Type | Constraints / meaning |
|---|---|---|
| `sequence` | integer | Positive, unique within a request; assigned in occurrence order |
| `requestId` | string | Required foreign key to the owning request |
| `node` | string | Non-empty execution node name |
| `payload` | object | JSON-compatible event data, excluding the separately stored `node` |
| `createdAt` | ISO 8601 timestamp | Event persistence time |

Trace events are returned in ascending `sequence` order. Each reconstructed event includes the `node` with its original event data so clients can consume the same trace shape as the chat response.

## Log Event

A single JSON Lines record for an operational event. It contains only allowlisted metadata, such as timestamp, level, event name, request ID, node, route, outcome, status code, duration, and prompt-token count. It has no user identifier, payload, message, arguments, observation, answer, exception message, or arbitrary spread of caller-supplied fields.

## Persistence relationships and validation

- One request has zero or more trace events.
- A trace event cannot exist without its request.
- `requestId`, status, timestamps, HTTP status, metrics, and event payload are validated at the store boundary before persistence or return.
- Persist structured values as JSON and validate decoded values before exposing them from HTTP.
- Do not hold a write transaction open while chat reasoning runs. Persist the initial request before execution, and use short transactions to atomically couple related event and request-state writes, including terminal status and completion metadata.
