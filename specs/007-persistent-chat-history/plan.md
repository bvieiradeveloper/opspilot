# Implementation Plan: Persistent Chat History

**Branch**: `007-persistent-chat-history` | **Date**: 2026-10-19 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/007-persistent-chat-history/spec.md`

## Summary

Allow callers to start and resume isolated chat conversations by identifier. Persist ordered user and assistant messages, compose at most the 12 latest prior messages into the next strategy request, and report the number of prior messages supplied as `metrics.historyMessages`. Add a SQLite-backed conversation store using the project's existing synchronous SQLite and validation patterns, inject it through the HTTP composition boundary, and verify behavior with an in-memory database and deterministic strategies.

## Technical Context

**Language/Version**: TypeScript 7, ESM, Node.js 22 LTS, strict mode.

**Primary Dependencies**: Express 5, Zod 4, LangChain/LangGraph, Node.js `node:sqlite`, and `tsx`; already declared or provided by the project.

**Storage**: SQLite through `DatabaseSync`, following the existing store conventions. A conversations table owns identifiers; a messages table stores ordered conversation messages and references their conversation.

**Testing**: `node:test` via `tsx`; run focused HTTP and store tests, then `npm run test` and `npm run typecheck`. Store tests use `:memory:`; HTTP integration tests inject a deterministic fake strategy and an isolated conversation store.

**Target Platform**: Node.js 22 LTS.

**Project Type**: Existing TypeScript Node.js application with an Express HTTP API and SQLite-backed stores.

**Performance Goals**: Load at most 12 prior messages for each chat request. No additional latency or throughput target is specified.

**Constraints**: Validate the optional conversation identifier at the HTTP boundary. Keep persistence and conversation rules outside the controller and reasoning strategies. Pass the bounded, role-tagged history through the existing strategy input alongside the current request. Preserve the existing chat response fields and metrics while adding `conversationId` and `metrics.historyMessages`. Reject unknown supplied identifiers rather than silently creating a conversation. No new dependency or external model access in tests.

**Scale/Scope**: Extend the existing `POST /chat` flow and response, add a conversation store with `create`, `append`, and `lastMessages` operations, persist messages in SQLite, and cover the behavior with isolated tests.

## Constitution Check

*GATE: Evaluated before Phase 0 research and re-checked after Phase 1 design.*

- **Schema validation**: PASS. Validate `conversationId` in the HTTP request and the expanded successful response at the boundary with Zod.
- **MVC boundaries**: PASS. Keep HTTP parsing/status translation in `src/http`, conversation lifecycle and prompt composition in a service, and SQLite access in a store model.
- **Test-first quality**: PASS. Cover storage with an in-memory SQLite database and the endpoint with fake strategies; run tests and typecheck.
- **Domain errors**: PASS. Represent an unknown conversation as a typed domain error and translate it to a clear client error at the HTTP boundary.
- **Secure and responsible operations**: PASS. Keep conversation data scoped to its identifier, bind all SQL values, do not expose internal errors or read `.env` directly in application code.
- **Technology constraints**: PASS. Use the existing Node.js `DatabaseSync` SQLite pattern, strict TypeScript, Express, Zod, and `node:test`; add no database server or package.
